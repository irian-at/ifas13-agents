gf1's ~11151 `countErrorFieldDiffs()` in GrossfileRecalculationTest are a benign return-file **representation** difference, not a calc error or data loss. Verified: 0 of the new-null diffs have a non-zero legacy value; `calculatedVsOldReturn` = 0 errors.

**Driver (two things combine):**
1. New system drops zero-valued country-vector entries for unreported countries — `CountryVector.filterZeroValuesForCountries` (CountryVector.java:165-179), via `JavaSteuerMeldungCalculator`/`SteuerMeldungPostProcessing.removeUnreportedCountries`. Written to return CSV → reloaded → entries absent (n.v.). Legacy always wrote explicit `0.0000` per country.
2. The `newReturnVsOldReturn` diff uses stricter `StmDiffConfigs.EXPECTED_OLD_RETURN_FILE_VALUES_VS_ACTUAL_NEW_RETURN_FILE_VALUES` where `actualMissingValueEqualsExpectedZero` / `actualMissingVectorEntryEqualsExpectedZeroVectorEntry` = **false**; the `calculatedVsOldReturn` config (`…VS_ACTUALLY_CALCULATED_VALUES`) has them **true** → 0 diffs. Same numbers, opposite verdict = config strictness.

**Why the dedicated tolerance never fires (verified 2026-07-31):** `KnownLegacySystemIssues.tolerateWronglyReportedZeroValueCountryCodes` was written for exactly this legacy over-cumulation bug, and its country set IS populated (`RecalculationDomainService.determineToleratedWronglyReportedZeroCountryVectors` — each STM gets the countries cumulated from the *preceding* STMs of the return file). But it guards on `legacyReturnValue instanceof CountryVector && newReturnValue instanceof CountryVector`; after the return-CSV round-trip the new side is **null**, not an empty vector → guard fails → `FieldDiffSeverity.ERROR`. It only downgrades "new vector exists but lacks some of legacy's zero countries". The other escape hatch, `knownOldReturnFileIssue`, *does* handle `actual == null` vs all-zero legacy vector → WARNING, but only for the 7 names in `OLD_RETURN_FILE_ISSUE_FIELDS` (of the `AS_*` block only `…nichterstattbareQuSt_mangelsDBA[_jeAnteil]`). Targeted fix if the noise ever needs silencing: treat a null new value as an empty CountryVector inside that guard — safe, since a non-zero legacy value still fails the `allMatch(isZero)` check. Do NOT instead flip the config flags (would also hide genuine dropped non-zero values).

Composition: 10783 from newReturnVsOldReturn (85 meldungen) + 368 from oldReturnVsNewReturn = 11151 (no reciprocal double-count). 93% is 77 meldungen × identical 135-field block of `D_/Z_/ZA_/AS_` (Dividenden/Zinsen/ZinsenAltemissionen/Ausschüttungen-Subfonds) breakdown fields, form `NEU = n.v. / ALT = [XX=0.0000]`. 3 STATUS_ANMERKUNG text notes are the only non-numeric.

**Re-baseline triggers:** flipping those config flags to true, or making the return-CSV writer emit explicit zeros like legacy — both collapse the count. Whether new system *should* emit explicit zeros is a Fachabteilung/format call (nothing lost substantively). Relates to [[project_recalc-historical-fidelity]].

**Resolution (2026-07-21):** GrossfileRecalculationTest's field-diff lockdown now counts ONLY `calculatedVsOldReturn` (private `countCalculatedVsOldReturnDiffs` helper streaming `steuerMeldungRecalculations()`), NOT `BundleRecalculationResult.countErrorFieldDiffs()` (which also sums the strict newReturn/oldReturn round-trip). All 8 grossfiles = FieldDiffExpectation(0,0) → the lockdown asserts "calculated STM matches legacy return field-by-field". The return-file representation noise (11151 etc.) is intentionally excluded.

**calculatedVsOldReturn is 0 even for real divergences** because when the new system escalates a meldung to ERROR it skips the Ermittlung (`calculatedSteuerMeldung` null → `calculatedVsReturnFileDiff` returns null; also legacy-return-status≠OPEN → ONlY_STATUS_FIELDS). So status escalations (new ERROR vs legacy NEW_DECLINED, e.g. gf1 LU0006391097, gf2 LU0891777665) show only as STATUS_STATUS/STATUS_ANMERKUNG diffs in the newReturn/oldReturn comparison + in the log-delta SummaryExpectation — not in calculatedVsOldReturn.

**Second lockdown added: StatusDiffExpectation** — counts STATUS_* diffs from `newReturnVsOldReturn` only (one direction; `countStatusReturnDiffs` filters `getDifferences()` on `fieldName().startsWith("STATUS")`). Baselines: gf1=(7,0), gf2=(2,0), gf5=(1,0), rest (0,0). Captures status escalations without the zero-vector value noise. Note: `_STATUS_*` defined names carry a leading underscore in SteuerMeldung.java but `FieldDiff.fieldName()` renders them without it, so `startsWith("STATUS")` matches. `calculatedVsOldReturn` never sees STATUS fields (its `IGNORE__STATUS_...` filter drops them); `newReturnVsOldReturn` uses `IGNORE__STB_SINGLE_FIELD_CODES` which keeps them.

**Legacy col-4 rule (C++ `c_st_meldung.cpp:12187` `WriteMeldung_STATUS`; CORRECTED 2026-07-23):** col4 = `nStm_id_vorherige`, written on every return status except the literal `CONFIRMED`/`DELETE` (those are only the separate confirm/delete files via `WriteConfirmMeldung`:11965). A confirmation's RETURN status is `FINAL` (GetNewStatus, callers 11887/11937), so the guard does NOT suppress it — **FINAL rows DO carry a ref**. The value of `nStm_id_vorherige` is operation-dependent: accepted UPDATE→OPEN = **immediate `vorherige_stm`** (:7878/:10613); CONFIRMED→FINAL and ERROR = **nearest FINAL ancestor** (validation walk :8825-8886 / :9157-9218 sets `nStm_id_vorherige = nStm_id_vorherigeFINAL = <FIN>`). Empty only when the relevant predecessor doesn't exist. Header: h:639 `nStm_id_vorherige` vs h:643 `nStm_id_vorherigeFINAL`. DB `vorherige_final_stm_id` maintained at :10995.

⚠️ EARLIER WRONG CONCLUSION (do not trust prior notes): "legacy never writes a ref on FINAL / col4 = immediate always." That was an artifact of the 8 grossfiles having only FIRST-time confirmations (no prior FINAL → nearest-final trivially null → empty). A real re-confirmation return file shows a FINAL row WITH the nearest-final ref. ⇒ neusystem CONFIRMED path keeps `vorherigeFinalStmId` in col4 (the `null` change was reverted 2026-07-23). ERROR path (`resolveErrorReferencedStmId` → nearest FINAL) is correct. The gf6 OPEN-row observation (ref=immediate open 649585) is still valid — but it's the OPEN-row rule, distinct from FINAL/ERROR (nearest final).

**Status-diff field breakdown (for re-baselining):** gf1 = 3×STATUS_STATUS + 3×STATUS_ANMERKUNG + 1×STATUS_MELDUNGS_ID (new uses sentinel 9999999999 vs legacy real id — recalc harness artifact); gf2 = 1×STATUS_STATUS + 1×STATUS_ANMERKUNG; gf5 = 1×STATUS_MELDUNGS_ID_REF (NEU=649528 / ALT=n.v. — the VorherigeFinalStmIdResolver populating the previous-final-STM reference where legacy had none). So `_STATUS_MELDUNGS_ID_REF` IS diffed+locked down, entirely as gf5's status count.
