The ISIN diff job crash is a shared Calendar, not bad data

Hibernate hands jTDS one JVM-wide static Calendar, and jTDS converts by writing into it. Any two threads touching a Sybase datetime corrupt each other.

What the stack trace actually says

It failed while exporting SteuerField rows, so the first suspicion was a broken guelt value in the fund being exported. The frame numbers rule that out.

public static long timeToZone(java.util.Date value, Calendar target) {
    GregorianCalendar cal = new GregorianCalendar();
    cal.setTime(value);                                 // the DB value
    target.set(Calendar.HOUR_OF_DAY, cal.get(...));     // 1298  read fine
    ...
    target.set(Calendar.DAY_OF_MONTH, cal.get(...));    // 1304  read fine
    return target.getTime().getTime();                  // 1305  threw
}

The throwing frame is Support.java:1305, and it works on target — Hibernate's static calendar — only after every read of the database value on lines 1298–1304 has succeeded. A corrupt datetime would have failed three lines earlier.

The array in Index 17 out of bounds for length 13 is the JDK's accumulated-days-per-month table. Arriving at month 17 means the calendar's own field state was inconsistent — the documented consequence of driving one Calendar from two threads.

The mechanism

Hibernate assumes a driver only reads the time zone off the calendar it is given. jTDS instead sets seven fields on it and calls getTime(). It is unfixed upstream: the static field is still there in Hibernate 7.1.8.

Why UTC is in play when the app is Vienna

Nothing in our code asks for UTC. hibernate.timezone.default_storage is unset, so the strategy is DEFAULT, which Hibernate resolves against the dialect — MetadataBuilderImpl.java:858-866, comment: "otherwise we normalize things to UTC".

DialectgetTimeZoneSupport()StrategyColumn typeCalendar handed to the driver
H2NATIVENATIVETIMESTAMP_WITH_TIMEZONEnone safe
PostgreSQLNORMALIZENORMALIZE_UTCTIMESTAMP_UTCyes, but pgjdbc copies only the zone safe

hibernate.jdbc.time_zone=Europe/Vienna never reaches those columns. It is consulted only by TimestampJdbcType, which serves LocalDateTime and LocalDate — the bulk of the schema. Note what that class does at TimestampJdbcType.java:110: Calendar.getInstance(options.getJdbcTimeZone()), a fresh calendar per call. The Vienna path was never exposed, because Hibernate already does there exactly what the fix does here.

Blast radius

Only offset- and instant-typed fields take the UTC path. On the Sybase units there are four:

  • SteuerField.guelt — what crashed; read for every fund the exporter touches
  • SteuerFieldFormel.guelt
  • Kest98.guelt
  • Land.validFrom — an Instant, and already carrying a // todo - change datatype!

The 13 OffsetDateTime fields on the infra entities use the same descriptor, but infra runs on PostgreSQL and H2, so they were never at risk.

The crash is the loud form. The quiet form is a read that silently returns another thread's timestamp — in the reproduction, a reader expecting 12:34:56Z got 12:35:00Z, 12:34:59Z and 12:35:02Z. Nothing logs that, and an export keeps the value.

The options we had

OptionWhat it doesVerdict
Switch the fields to ZonedDateTime Nothing. ZonedDateTimeJavaType and OffsetDateTimeJavaType carry the identical line, getDefaultZonedTimestampSqlType() no effect
hibernate.type.prefer_java_time_jdbc_types=true Maps to OffsetDateTimeJdbcType, which touches no Calendar at all — but it calls rs.getObject(pos, Class), and jTDS throws AbstractMethodError there (JtdsResultSet.java:1798) breaks every read
@TimeZoneStorage(NORMALIZE), or plain LocalDateTime Moves the four fields onto the Vienna path, which is thread-safe by construction and matches what getdate() writes right model, data decision
Replace the descriptor done Same conversion, one calendar per call no stored value moves

What is implemented

  • ThreadSafeTimestampUtcJdbcType — per-call Calendar, in bind and extract
  • ThreadSafeTimestampUtcTypeContributor — ServiceLoader, swaps the descriptor per persistence unit, only where the dialect registered the sharing one
  • Unit test driving the extractor through jTDS' real Support.timeToZone from 8 threads

Verified: the test fails when pointed back at Hibernate's descriptor, and TemporalTypeRoundtripTest stays 12/12 green on H2, PostgreSQL 15 and Sybase 16 — so no stored or read value changed. The startup log confirms it engages for Sybase and PostgreSQL and skips H2.

Worth keeping even if we later move the four fields: the defect is upstream and invisible, so the next OffsetDateTime on a Sybase entity would re-arm it, with an AIOOBE in JDK calendar code as the only symptom.

The open question for us

On Sybase, steuer_fields.guelt is datetime default getdate() (V005__vorgabe.sql:45). getdate() is server local time. So the same column holds Vienna wall clocks from legacy and from the column default, and UTC wall clocks from every row the new system wrote — one to two hours apart, with nothing marking which is which.

Leave it on UTC

→ No migration, no fixture churn. We document the split and accept that guelt means different things per writer.

Move the four to Vienna

→ One storage meaning, aligned with legacy, and off the racy descriptor for free. Needs a decision on existing rows.

What to settle before touching it:

  1. Do the existing rows need converting, or is guelt only ever compared, never displayed?
  2. Does anything outside IFAS13 read these columns and assume Vienna?
  3. The YAML export fixtures the diff jobs compare against encode the current values — they move with the mapping.
